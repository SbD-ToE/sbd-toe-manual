# KPIs and Metrics - Monitoring and Operations

## Scope and purpose {#âmbito-e-propósito}

The indicators of this domain assess the **operational effectiveness of the security monitoring programme**: the coverage of centralised logging, the quality of the alerts, the speed of detection and response, and the capacity for correlation between sources. This domain operates on data produced by all the other chapters - the logs generated by the code (Ch. 06), by the pipeline (Ch. 07), by the containers (Ch. 09) and by the infrastructure (Ch. 08) converge here and are assessed for their operational usefulness.

> This file is the **canonical catalogue** of `OPS-Kxx`. The file [`07-metricas-indicadores.md`](./07-metricas-indicadores.md) is a lighter operational synthesis for day-to-day use.

The central distinction of this domain: the `LOG-` requirements (Ch. 02) define what the software must record; the `OPS-K` indicators measure whether those records are centralised, analysed and acted upon effectively. A system with perfect logging but no correlation, alerts or response has zero visibility from an operational point of view.

The OPS indicators feed the cross-cutting dimension **T-03 (Resolution speed)** - specifically operational MTTD and MTTR.

---

## Denominator and portfolio foundation {#denominador-e-fundação-de-portfólio}

The indicators of this domain use as their denominator **F-02 - applications with a formal risk classification** (Ch. 01, CLA-K01). The percentages are interpretable only in relation to the set of applications classified at the relevant risk level - not in relation to the total portfolio or to ad-hoc subsets.

See `kpis-governanca.md` - section "Portfolio foundation" - for the SbD-ToE adoptability funnel and the relation between denominators.

## Complementary definitions {#definições-complementares}

**OPS-K01 - Centralised logging:** logging is considered centralised when security events are sent to a central collection system (SIEM, log aggregation platform) with retention, indexing and query capability. Local logging without forwarding does not satisfy this criterion.

**OPS-K02 - Tested alert:** an alert is tested when there is evidence that its threshold was validated in a real or simulated environment and that it produces the expected behaviour (a true-positive alert with sufficient context for triage). Alerts generated by tool defaults without review and calibration do not satisfy this criterion.

**OPS-K03 - MTTD (Mean Time to Detect):** measured as `timestamp_alerta − timestamp_evento`. For events that do not generate an immediate alert (detection by correlation or periodic analysis), the detection timestamp is the moment at which an analyst becomes aware of the event. Events without a recorded occurrence timestamp cannot be included in the calculation - their absence is in itself an indicator of a logging gap.

**OPS-K04 - MTTR (Mean Time to Respond):** measured as `timestamp_primeira_acção − timestamp_alerta`. The first action includes: isolation, blocking, formal escalation, or activation of a runbook. Analysis time before the first action counts towards the MTTR.

**OPS-K05 - Noise rate:** a false positive is an alert that, after formal triage by an analyst, is classified as irrelevant to the security context. A high noise rate has two effects: (a) it consumes response capacity; (b) it creates desensitisation to alerts, increasing the risk of ignoring true positives. Alert calibration is the control mechanism.

**OPS-K06 - Correlation between sources:** critical events (anomalous authentication, data exfiltration, privilege escalation) gain context and reduce false positives when correlated across, for example: authentication logs + network logs + application logs. The minimum coverage for L3 must include correlation between endpoint, network and application.

**OPS-K07 - IRP activated:** the formal incident response process (Incident Response Plan) is activated when there is a ticket or record with: the classification of the incident, a response owner, a timeline of actions, and a resolution state. Incidents resolved informally without a record do not satisfy this criterion.

**OPS-K08 - Retention in line with regulation:** the applicable minimum period depends on the sectoral regulation. Base reference: DORA requires 2 years for ICT logs; NIS2 does not define a period but requires availability for audit. Systems without a regulatory classification apply the internal policy - a minimum of 90 days for L1, 1 year for L2, 2 years for L3.

## MTTD/MTTR thresholds by level - summary {#thresholds-de-mttdmttr-por-nível---resumo}

| Metric | L1 | L2 | L3 |
|---------|:--:|:--:|:--:|
| MTTD (detection) | ≤ 24h | ≤ 4h | ≤ 30min |
| MTTR (response) | ≤ 48h | ≤ 4h | ≤ 1h |

These thresholds apply to security events of high/critical severity. For events of medium severity, the thresholds may be 3× higher. Regulated sectors (financial, health, critical infrastructure) may have more demanding requirements under sectoral rules.

## Collection and instrumentation {#recolha-e-instrumentação}

| Indicator | Primary source | Reference tools | Automation |
|-----------|---------------|--------------------------|-----------|
| OPS-K01 | Application inventory + SIEM configuration | SIEM (Splunk, Elastic, Sentinel, QRadar) | Partial |
| OPS-K02 | Alert register with calibration metadata | SIEM + alert documentation | No |
| OPS-K03 | Event log + alert log with timestamps | SIEM (automatic MTTD calculation) | Yes |
| OPS-K04 | Alert log + response action log | SIEM + IR system (PagerDuty, JIRA) | Yes |
| OPS-K05 | IR platform with triage classification | SIEM + triage documented by an analyst | Partial |
| OPS-K06 | Correlation rule configuration in the SIEM | SIEM (count of rules with multiple sources) | Partial |
| OPS-K07 | Incident database | IR system (ServiceNow, Jira, PagerDuty) | Yes |
| OPS-K08 | Retention configuration + system inventory | Retention policy audit per source | Partial |
